CVIT: system overview and CPU6 porting guide

A small, single-user, single-program environment: a resident kernel, a disk-loaded command interpreter, a flat filesystem, and loadable applications.

Baseline: Dusky/CVIT Nova sources as of November 8, 2026. Target: Centurion CPU6 with Hawk disk blocks of 400 bytes.

Status distinction. Nova behavior below describes implemented code. The CPU6 ABI and Hawk mapping are a proposed implementation contract, not a claim that a CPU6 port already exists or a description of an existing Centurion disk format. Instruction encodings, controller registers, disk geometry, bootstrap entry, and CPU6 memory layout must be established from the target's hardware documentation.

1. Core features and ownership

LayerResponsibilities
Resident kernelCold start; finding and loading COMMAND; warm start that reloads COMMAND; blocking console input; character and string output; raw block reads/writes; service dispatch; halt.
COMMANDThe ] prompt; command input and echo; case-insensitive verbs/member lookup; STA, CAT, TYPE name, RUN name; EOT exit.
FilesystemOne volume header, one flat directory, contiguous file extents, ten-character member names, text/binary/system member types, explicit length/load/entry metadata.
ApplicationsUse kernel I/O and return through warm start. Nova examples include a calendar and FOCAL with software floating point.
Host toolsAssemble and package programs, calculate directory metadata, allocate contiguous extents, generate images. Runtime file creation is not required.

Not part of the core: multitasking, processes, memory protection, dynamic allocation, hierarchical directories, file handles, runtime file creation/deletion, filesystem repair, or a scheduler. A block-write primitive does not imply a writable file API. FOCAL is an application, not a kernel service.

The minimum useful CPU6 milestone is boot → COMMAND → STA/CAT/TYPE → RUN → warm return. A FOCAL port is a separate, larger application milestone; Nova machine code cannot run unchanged on CPU6.

Required target facts before writing the driver

  • CPU6 register/call/return conventions, address units and width, byte order, interrupt behavior, and usable RAM map.
  • Console register addresses or firmware calls, ready/error bits, acknowledgment sequence, and terminal configuration.
  • Hawk controller command/status interface, unit selection, seek/read/write sequencing, completion/error bits, retry/reset procedure, and write protection.
  • Whether 400 bytes are controller-visible data bytes excluding any controller-managed framing, ECC, or headers; any transfer alignment or DMA restrictions.
  • Disk geometry and sector numbering, reserved tracks/blocks, and the exact CVIT partition base and length. Never assume a whole existing Hawk pack is available.
  • Where the initial loader resides and how it locates the kernel. CVIT logical block 0 is a volume header, not executable bootstrap code.

Keep these dependencies behind console and block-device routines. COMMAND and the filesystem should never manipulate controller registers directly.

3. Boot and warm-return sequence

Implemented Dusky path

scripts/run-dusky.sh
  build Dusky; assemble/package COMMAND and FOCAL
  make volume containing COMMAND, FOCAL, README.MD, HELLO
  convert TC08 staging image to DSK image
  start Snova --console image
    attach DSK0
    assemble simh/cvit-kernel-simh.asm at 0o1000
    set PC = 0o1000
      COLD: print kernel banner
      LOADCMD: read directory block 1 into kernel directory buffer
        find exact space-padded name COMMAND
        read its contiguous payload blocks at the recorded load address
        jump to recorded entry address
      COMMAND: initialize workspace; print banner and ] prompt

The current loader uses fixed directory block 1 and ten entries; it does not discover arbitrary layouts from the header. It reports ?DSK on disk failure or ?NOCMD on a missing member, then halts. It does not comprehensively validate malicious or corrupt metadata.

CPU6 contract

  1. External bootstrap loads the native kernel. Initialize kernel workspace, console and disk hardware to a known state; select the boot volume.
  2. Cold start prints a banner. Validate the volume header and bounds, read the directory, and locate COMMAND.
  3. Validate its type, extent, length, load range and entry point. Load its native image without overwriting resident state.
  4. Transfer control to COMMAND, which initializes all its mutable state and prompts.
  5. RUN loads an application and jumps to it. The application exits by jumping to kernel warm start, not by returning through a saved COMMAND stack frame.
  6. Warm start restores the kernel's required execution state and reloads COMMAND from disk. It must not depend on COMMAND or application workspace surviving.
  7. EOT at the COMMAND prompt calls kernel quit. Define whether target quit halts or returns to the hardware monitor.

Warm start is a destructive restart of the shell, not a process context switch. Application data is not preserved automatically.

4. Kernel service interface

The portable requirement is the service behavior, not the Nova register assignment. The CPU6 port must publish fixed entry stubs or a versioned dispatch table with a stable native address.

ServiceNova vector (octal)Required behavior
COLD0o1000Initialize/start the system and load COMMAND; no normal return.
WARM0o1001Reload COMMAND and jump to it; no normal return.
SYSCALL0o1002Dispatch a service number; reject unsupported selectors.
QUIT0o1003Halt or leave to monitor; no normal return.
READBLK / WRITEBLK0o1004 / 0o1005Synchronous transfer of one logical filesystem payload; caller specifies unit, block and buffer.
GETC0o1006Wait for one character; return its byte value. Do not echo inside GETC.
PUTC0o1007Output one byte. No implicit newline translation.
PUTS0o1010Output a zero-terminated string. Nova uses one character per word; CPU6 should define native byte strings explicitly.

Nova calling convention (reference only)

  • Calls use JSR through a pointer to the service; AC3 holds the return link.
  • Direct block calls: AC2 points to three words: drive, logical block, memory address. GETC returns AC0; PUTC consumes AC0; PUTS consumes AC2.
  • Dispatcher: AC0 is selector, AC1 is argument pointer. Selectors: 1 PUTC (character at argument word 0), 2 GETC, 3 PUTS, 4 READBLK, 5 WRITEBLK.
  • In the DSK implementation, direct and dispatched block operations return AC0 = 1 on success, 5 on failure. Dispatched PUTC/PUTS return 0; GETC returns the character. Do not assume all successful syscalls return zero.
  • Routines use static return/work cells and are not reentrant. Assume scratch accumulators and condition state can be destroyed unless a particular service guarantees otherwise.

Recommended CPU6 ABI decisions

Use native pointers and native-width block numbers, with explicit unit and buffer fields. Define register preservation, stack ownership, interrupt policy, string encoding, argument sizes and result locations in an assembler include shared by kernel and applications. A simple new ABI can normalize all I/O status to zero = success and nonzero = error; this is intentionally different from Nova's block status and requires new callers. Keep hardware status available for diagnostics. Disk operations should have bounded waits and a documented retry policy rather than polling forever.

5. Disk format and Hawk 400-byte mapping

Recommended first port: preserve the Nova filesystem's 128 × 16-bit-word (256-byte) logical payload, storing one logical block in each 400-byte Hawk block. This sacrifices capacity but avoids changing every directory, TYPE and loader calculation while bringing up new hardware.
TransportPhysical data sizeCVIT payloadRemainder
TC08 staging image258 bytes (129 words)First 256 bytes2 unused bytes
Nova DSK image512 bytes (256 words)First 256 bytes256 ignored bytes
Proposed Hawk compatibility image400 bytesFirst 256 bytes144 reserved bytes, zero on generated writes

All sizes in this section are decimal. A 400-byte block is 200 16-bit words, not 400 words and not 256 words. This guide does not assume that the CPU6 is word-addressed.

Hawk block B, relative to a reserved CVIT partition:
  bytes   0..255 : canonical CVIT payload
  bytes 256..399 : reserved, zero when written; ignored on read

physical address = controller_map(partition_base + B)
require 0 <= B < partition_block_count

A file occupying N logical blocks occupies N Hawk blocks. This is one-to-one mapping, not a packed stream spanning physical-block boundaries. Do not copy a 258-byte or 512-byte image directly onto Hawk and expect block numbers to remain valid.

Driver adapter and buffer safety

read_payload(unit, B, destination[256]):
  check unit and partition bounds
  hawk_read400(unit, partition_base + B, bounce[400])
  if failed: return error without publishing partial data
  copy bounce[0:256] to destination
  return success

write_payload(unit, B, source[256]):
  check bounds and write permission
  copy source to bounce[0:256]
  fill bounce[256:400] with zero
  hawk_write400(unit, partition_base + B, bounce)
  return completion status

Reserve a 400-byte hardware-compatible bounce buffer in resident memory. Do not transfer 400 bytes directly into a 256-byte caller buffer. In contrast, Nova's current DSK loader reads 512 bytes directly at each destination while advancing by only 256 bytes; it requires 256 bytes of sacrificial headroom after the loaded extent. The bounce-buffer CPU6 contract removes that dependency.

Canonical payload encoding

Preserve the version-1 disk encoding for the compatibility profile: every 16-bit field is serialized little-endian, independent of CPU6 native byte order. In memory, decode fields explicitly or use accessor routines. Names pack the first character into a word's high byte, so their raw byte order differs from ordinary ASCII strings.

Example: name AB produces word 0x4142, serialized as bytes 42 41. Header word CV is 0x4356, bytes 56 43. Do not compare raw disk name bytes against an ordinary character string without decoding.

Volume layout and header

Logical block 0 is the header; block 1 is the directory; file data starts at block 2. Each header field below is a 16-bit word; byte offset = 2 × word offset.

Word offset (decimal)Value

4Directory block count = 1

The CV/NV signature is retained as a compatibility identifier; it does not identify the executable instruction set. Use only CPU6-built SYS members on a CPU6 volume. Version 1 has no architecture tag.

Directory entries

There are ten 24-byte entries in the directory payload; the final 16 payload bytes are zero. An unused entry has a zero first name word. Entries contain no fragmentation chain: every file is one contiguous extent.

Word offset (decimal)Byte offset (decimal)Meaning
0–40–9Ten-character uppercase name, space-padded, two characters packed per word as described above.
510Type: 1 = TXT, 2 = BIN, 3 = SYS.
612Start logical block.
714Allocated logical block count.
816Load address, interpreted by the target architecture.
918Entry address, interpreted by the target architecture.
1020Length in 16-bit storage words. TXT has one character per storage word, so this also equals its character count.
1122Reserved, zero.

All fields are unsigned 16-bit values. Maximum recorded length is 65,535 storage words. Check arithmetic with wider intermediates. The Nova builder masks serialized fields to 16 bits; a CPU6 builder should reject overflow rather than silently truncate.

File representation and allocation

  • TXT: each input byte becomes a 16-bit word with its high byte zero. Thus a full payload contains 128 text characters, not 256. Length excludes padding. LF is translated to CR+LF during TYPE, not during storage.
  • BIN/SYS: arbitrary bytes grouped into little-endian storage words. An odd final byte is padded with zero; the word-length field cannot preserve the original odd byte count.
  • Allocate max(1, ceil(length_words / 128)) blocks. Empty files still consume one block in the current builder. Zero-fill the last block beyond the valid length.
  • Names are 1–10 characters, uppercased and space-padded. The target builder should restrict names to an agreed printable ASCII subset and reject duplicates after normalization.
  • Only one directory block and ten entries are supported in this baseline; there are no subdirectories or runtime allocator.

Do not silently expand the payload to 400 bytes

A native 400-byte-payload filesystem would offer 200 words/block, 16 complete 24-byte entries per block, and 288 fewer wasted bytes per two physical blocks than this compatibility mapping. It would also require changes to header capacity, directory scan limits, extent calculations, load increments, TYPE loops, builders and validators. That is a separate, explicitly versioned format; it is not defined here. Start with the compatibility profile, then design a native format if the extra capacity is needed.

6. Native program format and memory ownership

Nova reference: COMMAND is packaged as [n1][n1 page-zero words][code...]. Entry is load + 1 + n1 in Nova word addresses. Its prologue copies page-zero initialization words to 0o0050. FOCAL uses a different startup trailer containing page-zero start/count/data. These are Nova implementation techniques, not portable executable formats.

Proposed minimal CPU6 executable profile

  • Use a flat native byte image, assembled for a fixed target load address. No runtime relocation, no implicit page-zero restore, and no Nova prefix.
  • For this profile, directory load and entry fields are 16-bit CPU6 byte-address offsets within one documented execution window. If the target needs wider or banked addresses, define that window/selector outside the file before implementation, or design a new executable format; do not truncate addresses.
  • Store CPU6 instruction/data bytes unchanged as a byte stream in BIN/SYS payloads. The little-endian metadata encoding does not require swapping native instruction bytes. Storage length is ceil(image_bytes / 2); an odd image gets a trailing zero byte.
  • Require COMMAND and RUN members to be SYS. Entry must fall inside the initialized image. Validate that its entire extent and destination range are in bounds, non-wrapping, and do not overlap resident code, kernel data, bounce buffer, active loader state, or required stack.
  • Advance disk block by one and destination byte address by 256. Copy only min(256, remaining_storage_words * 2) valid bytes on the final block. Rounded image padding must be harmless.
  • Applications initialize their own workspace/stack. No implicit register values other than the documented ABI are promised. On exit, jump to WARM; do not expect COMMAND's registers or variables to survive.

Before coding, draw a target memory map with resident kernel, vectors, stack, directory buffer (256 bytes), disk bounce buffer (400 bytes), shell, and application regions. If RUN is allowed to overwrite COMMAND, all code and variables needed to finish the load and jump must first be moved to resident memory. The current Nova RUN loop resides in COMMAND, so it is not a general overlap-safe loader.

Nova reference addresses are word addresses: kernel 0o1000, directory buffer 0o2000, COMMAND 0o3000, FOCAL 0o6000, shell block scratch 0o7600. Do not reuse these numerical values as CPU6 byte addresses without a new memory-layout design.

7. COMMAND behavior

InputBehavior
STARead header block 0 and check volume signature; report readiness or invalid-volume/disk error. The CPU6 port should also validate version and fixed layout.
CATRead directory block 1; display nonempty names in directory order.
TYPE nameFind normalized name, save metadata before reusing directory scratch, and stream only valid data. TXT emits each word's low byte with LF → CR+LF; BIN/SYS emit low then high byte per word with no newline conversion.
RUN nameFind member, require SYS, validate/load extent, jump to entry. No saved shell context.
EOT (0x04)At COMMAND input, quit/halt. Inside an application, interpretation belongs to that application; FOCAL uses it to return to COMMAND.
Unknown commandPrint ?WHAT, then prompt again.

Normalize ASCII case, not arbitrary binary payloads. Use CR (0x0D) to submit a line; emit explicit CR+LF for terminal newlines. A CPU6 shell should bound its input buffer, discard or reject excess input safely, and define backspace/rubout handling. The Nova shell's small line workspace and simplistic parser are not a safe general parser specification. Full volume/library path syntax is future work; implement a single boot-volume member name first.

Useful compatible diagnostics include ?DSK, ?NOCMD and ?SVC. Add clear invalid-image/range errors for the CPU6 validator. On an application load failure after the shell has been overwritten, recover through resident WARM or stop safely; never jump into a partially loaded image.

8. Bring-up and acceptance checklist

  1. Console: transmit a fixed banner, receive/echo characters, test CR/LF, EOT and terminal buffering. Verify hardware acknowledgments do not repeat or lose characters.
  2. Read-only Hawk driver: read a known test block repeatedly, confirm all 400 bytes, verify partition bounds and controller error handling. Use a scratch pack/partition.
  3. Adapter: generate known 256-byte payloads, wrap into 400-byte blocks, compare reads byte-for-byte. Test the boundary between adjacent blocks and guard bytes around all buffers.
  4. Filesystem: check exact header/name encodings; list zero, one and ten entries; reject bad signatures/version, overflowed or out-of-volume extents, overlapping reserved blocks, and duplicate names.
  5. TYPE: empty, short, exactly 128-character, 129-character and multi-block TXT; BIN with distinct low/high bytes and final padding. Assert complete output and correct stopping at length.
  6. Loader: launch a tiny native program that prints and jumps to WARM. Test missing COMMAND, non-SYS RUN, disk failure halfway through loading, illegal entry, and attempted kernel/buffer/loader overwrite.
  7. Warm return: run an application that deliberately destroys shell workspace, return, then CAT/TYPE/RUN again. Verify the boot directory control block is unchanged across warm starts.
  8. Writes, last: on disposable media only, write/read back a block, verify neighbors and reserved tail bytes, and exercise write-protect/failure status. Do not overwrite an existing Centurion filesystem.
  9. Regression: compare complete expected terminal transcripts and require successful completion. Treat timeout as failure, not successful test termination.

9. Source map and known documentation traps

  • simh/cvit-kernel-simh.asm: active DSK kernel, fixed service vectors, console driver, block driver and COMMAND loader.
  • simh/cvit-command-simh.asm: active COMMAND implementation and RUN/TYPE logic.
  • scripts/run-dusky.sh and dusky/Program.cs: host-assisted boot and console execution.
  • scripts/mk_cvit_nova.py: authoritative version-1 image encoding. No Hawk writer currently exists.
  • scripts/abs2bin.py and scripts/abs2flat.py: Nova-specific executable packaging, not CPU6 assemblers.
  • Nova notes, filesystem specification, FOCAL, and bring-up friction log.

When prose conflicts with code, inspect the current implementation. Older notes describe 11-word directory entries (the format actually uses 12), no return from RUN (warm return now exists), or uniformly zero success status (DSK block calls actually return 1). Nova assembly defaults to octal: directory length is decimal word offset 10, written 0o12, not octal 10. Explicit units, named offsets and two-sided branch tests prevent costly porting errors.

CPU6 portability is at the service and filesystem level, not at the binary or device-register level. Keep the first port small, bounded, and independently testable.
